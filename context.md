# claude-sync: контекст и решения

## Задача

Основное место работы: ноутбук и комп. VPS (две: основная и запасная, живут одновременно) нужны по мере надобности, когда пришлось внезапно уйти от компа.

Нужна небольшая веб-морда на VPS:
- показывает существующие сессии Claude Code (название + `cwd`, откуда сессия запускалась);
- по кнопке делает resume выбранной сессии с Remote Control, дальше работа идёт с телефона через приложение Claude;
- по кнопке останавливает сессию.

Морда удобнее Termux + скриптов: с телефона на ходу проще открыть страницу, чем возиться руками. Скрипты годятся только для проверки флоу до написания кода.

## Стек

- Rust + axum.
- HTML-шаблоны: `askama` (шаблоны в отдельных `.html`-файлах, проверяются на этапе компиляции, для htmx-фрагментов удобно разбивать на мелкие шаблоны). Интеграция с axum через `askama_web` (фича `axum-0.8`) или ручной `Html(tpl.render()?)`.
- htmx для интерактивности (атрибуты `hx-post`/`hx-swap` дёргают сервер и вставляют в страницу пришедший HTML-кусок). Без React, без сборки фронта, без JSON API.
- Статика вшивается в бинарь (`rust-embed` или `include_str!`).

## Окружение

**Решение для MVP:** морда, tmux и claude работают на хосте VPS под пользователем `aragami3070`, морда как systemd-сервис. Docker отложен: всё ручное тестирование было на хосте, контейнер добавляет неизвестные (логин, монтирование, тулчейны). Пункты ниже про Docker относятся к возможному следующему шагу.

**Другие люди на той же VPS:** отдельный Linux-пользователь на каждого (свой `~/.claude` и логин Claude, свой `syncthing@<user>`, свой tmux-сервер, свой экземпляр морды на своём порту под своим пользователем со своими кредами). Общую морду под root не делать. Имя пользователя (путь к home) должно совпадать с их локальным. В группу `docker` и `sudo` не добавлять (`docker` = root). Диск 40 ГБ общий.


- Docker-контейнер на VPS, в котором есть обе директории: `~/projects` (git-клоны проектов) и `~/.claude/projects` (транскрипты, auto memory, через Syncthing).
- Пути один в один с нодами: проекты монтировать в `/home/aragami3070/projects/...`, `~/.claude` в тот же `$HOME`. Имя каталога проекта в `~/.claude/projects` получается из абсолютного пути.
- `cwd` сессии брать из поля `cwd` в jsonl, а не декодировать имя каталога: декодирование неоднозначное (`-` и `/`).

## Синк

- `~/.claude/projects`: Syncthing между всеми нодами (ноут, комп, обе VPS).
- Код: **только git**, Syncthing код не трогает. Resume делает `git pull --ff-only`, при грязном дереве или разошедшихся ветках морда показывает ошибку. Syncthing рабочей копии вместе с `.git` между 4 нодами грозит битым репозиторием.
- Если проекта ещё нет на VPS, его клонирует локальный скрипт по ssh (после MVP, см. «Открытые вопросы»). Морда в этом случае просто показывает ошибку «нет репозитория в `cwd`».
- WIP-коммит/ветку перед уходом делаю сам, автоматизация хуками не нужна.
- Защита от двойного запуска сессии не нужна: если сессия жива на ноуте, иду в неё через приложение, а не через морду.
- Syncthing на VPS — пользовательский сервис, ему нужен `loginctl enable-linger` (без него синк шёл только пока открыт ssh; `sudo` у пользователя нет, команду надо выполнять под root). Морде linger не нужен: она системный сервис, tmux живёт в её cgroup.
- Если одна сессия случайно поднята на двух VPS, Syncthing создаст `.sync-conflict` копии jsonl. Помнить про это, но кода под это не писать.

## Управление сессиями

`claude` это интерактивный TUI, ему нужен PTY, поэтому процессом управляем через tmux:
- **Список:** чтение jsonl: `id`, `title` (из `/rename` или первое сообщение), `cwd`, mtime, сортировка по свежести.
- **Статус:** `tmux ls` / `tmux has-session`.
- **Resume:** подготовка git (см. «Git на VPS») → `tmux new -d -s <id> 'claude --resume <id> --remote-control'`. Ссылку на RC-сессию вытащить через `tmux capture-pane` и показать кнопкой «открыть в приложении».
- **Stop:** `/exit` через `send-keys`, при таймауте `kill-session` → WIP-ветка и push (см. «Git на VPS») → `cargo clean` по git root этого `cwd`, если в проекте не крутится другая сессия.
- Плюс tmux: сессии переживают рестарт сервера, к ним можно подключиться по ssh (`attach`).

## Git на VPS

Сценарий: на VPS через RC идёт работа (например, разбор дейликов), VPS коммитит, а я потом локально коммичу или форс-пушу поверх и затираю её работу.

Правило: **VPS никогда не пишет в мои ветки и никогда не делает `--force`.** Её работа уезжает только в отдельные ветки `vps-wip/<session-id>`. Так одинаково для master и для любой другой ветки, отдельного случая «есть только master» нет.

- **Resume:**
  - если есть `origin/vps-wip/<session-id>` (эту сессию уже возобновляли на VPS, а я ещё не влил результат), то `git switch` на неё и `pull --ff-only`, чтобы код совпадал с тем, что помнит транскрипт;
  - иначе `git pull --ff-only` текущей ветки.
- **Stop:**
  1. Если дерево грязное или есть коммиты сверх upstream: `git switch -C vps-wip/<session-id>`, `git commit -am` (в сообщении id и title сессии), `git push -u origin vps-wip/<session-id>` (обычный push, без force).
  2. **Только если push прошёл:** вернуться на исходную ветку, `git reset --hard origin/<ветка>`, удалить локальную wip-ветку. Клон на VPS снова чистое зеркало remote, следующий `pull --ff-only` всегда пройдёт.
  3. Если push упал: ничего не сбрасывать, показать ошибку в морде.
- Session-id в имени ветки: повторный resume той же сессии дописывает в ту же ветку fast-forward'ом, ветки двух VPS не пересекаются, коллизий с моими ветками нет.
- Дома: `git fetch` → вижу `origin/vps-wip/*` → merge/rebase/cherry-pick к себе → удаляю ветку на remote. Можно сделать alias или подсветку в prompt, чтобы не забыть про неслитые wip-ветки.
- `--force` с ноута по своим веткам больше ничего не теряет: работа VPS лежит в другой ветке.

## Безопасность

- Доступ только через VPN. Креды basic auth передаются через `.env` при запуске контейнера.
- VPN: AmneziaVPN (автонастройка, AWG в контейнере `amnezia-awg2`). Клиенты в `10.8.1.0/24` внутри контейнера, хост VPS виден из туннеля как `172.29.172.1` (bridge `amn0`, Docker-сеть Amnezia). **Проверено:** с ноута под VPN `curl http://172.29.172.1:<port>` работает, без VPN таймаут.
- **Docker обходит ufw**: порт морды публиковать только на `172.29.172.1` (`"172.29.172.1:8080:8080"` в compose), не на `0.0.0.0`.
- Syncthing: адрес VPS на нодах `tcp://172.29.172.1:22000`, наружу ничего не открывать. Желательно ограничить listen address Syncthing на VPS тем же адресом или включить ufw (не забыв `22/tcp` и UDP-порт Amnezia).
- Если Amnezia переустановить, подсеть `amn0` может смениться, тогда адреса придётся поправить.
- Для push контейнеру нужен свой ssh-ключ (deploy key) к remote'ам.
- Транскрипты хранятся открытым текстом и могут содержать секреты.

## Docker и Claude Code в контейнере

- RC требует логин через claude.ai (`claude auth login`, `setup-token` не подходит). Один раз залогиниться интерактивно в контейнере, credentials хранить в volume. На каждой VPS логин свой.
- Trust-диалог при первом запуске в новой папке, скорее всего, нельзя пройти через RC. Обход: заранее прописать доверие в `~/.claude.json`. **Проверить.**
- Автообновление claude выключить, обновлять пересборкой образа.
- В образе нужны тулчейны проектов (rust, node и т.д.), иначе Claude не сможет собирать и гонять тесты.

## Место на диске (лимит 40 ГБ вместе с target'ами)

- База `debian:trixie-slim`, не alpine. Alpine экономит ~70 МБ при тулчейне 1–1.5 ГБ и добавляет проблем с musl: Claude Code на Alpine требует `libgcc`, `libstdc++`, системный `ripgrep` и `USE_BUILTIN_RIPGREP=0`; крейты вроде `openssl-sys` капризничают.
- `rustup --profile minimal`, без docs (~−600 МБ).
- В env контейнера: `CARGO_INCREMENTAL=0` и `CARGO_PROFILE_DEV_DEBUG=0` (или `line-tables-only`). Target худеет в разы.
- `cargo clean` на стопе сессии (см. «Управление сессиями»).
- `~/.cargo/registry` в volume, иногда чистить (`cargo cache -a` или cron).
- Периодически делать `docker builder prune` / `docker image prune`.

## Что не надо делать

- React.
- Логику failover между двумя VPS: запасная это тот же compose и та же синк-папка, запуск вручную.
- Защиту от двойного запуска сессии.
- Хуки для автоматических WIP-коммитов.

## Что Claude Code уже даёт сам

- Чат с телефона, подтверждение разрешений, пуши: RC + приложение Claude.
- Новые сессии с телефона: `claude remote-control` (server mode). Resume **существующей** сессии он не умеет, эту дыру и закрывает морда.
- Названия сессий: `/rename`, пишется в jsonl.

## Ручная проверка на VPS (2026-10-19, на хосте, без Docker)

1. ✅ Синк транскрипта ноут → VPS через Syncthing, `claude --resume <id>` на VPS видит историю.
2. ✅ `tmux new -d -s t1 "claude --resume <id> --remote-control"` работает, сессия видна в приложении на телефоне, промпты с телефона доходят.
3. ✅ Обратный синк VPS → ноут: переписка с телефона видна при resume на ноуте.
4. ✅ Trust-диалог для новой папки: работают оба обхода.
   - **Выбрано:** перед запуском морда прописывает trust в `~/.claude.json` (атомарно: запись во временный файл, `chmod 600`, `mv`; только если `hasTrustDialogAccepted` ещё не `true`):
     `jq --arg p "<cwd>" '.projects[$p] = ((.projects[$p] // {}) + {hasTrustDialogAccepted: true})'`
   - Запасной вариант: `tmux send-keys Down`, потом `Enter` (по умолчанию выбран `No, exit`). Хрупко: сломается, если поменяется порядок пунктов.
   - Риск: запущенные claude тоже перезаписывают `~/.claude.json` и могут затереть правку или словить гонку. На практике редко, но при ошибке trust-диалог просто появится снова. Его видно через `capture-pane`, и морда может показать «висит trust-диалог».
5. В тесте A при первом запуске в папке на VPS был именно trust-диалог, других стартовых диалогов не было.
